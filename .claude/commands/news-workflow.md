# 뉴스 수집기 새 기능 개발 워크플로우

아래 단계를 **순서대로** 실행한다. 각 단계가 끝나기 전에는 다음 단계로 넘어가지 않는다.
브랜치 이름 입력값: `$ARGUMENTS`

## 1단계: 상태 확인

1. `git status`와 `git branch --show-current`로 현재 브랜치와 작업 트리 상태를 확인한다.
2. 현재 브랜치가 `main`이 아니면:
   - 경고를 보여준다: "⚠️ 현재 브랜치는 `<현재 브랜치>`입니다. 새 기능 브랜치는 main에서 시작해야 합니다."
   - "main으로 이동할까요?"라고 사용자에게 묻고, **답을 기다린다.**
   - 승인하면 `git checkout main`을 실행한다. 거절하면 워크플로우를 중단한다.
   - 커밋되지 않은 변경 사항이 있어 이동이 실패하면, 변경 사항을 알려주고 사용자에게 처리 방법을 묻는다. 임의로 버리거나 stash 하지 않는다.
3. main이라면 작업 트리가 깨끗한지 함께 알려준다. 변경 사항이 있으면 사용자에게 알리고 계속할지 묻는다.

## 2단계: 새 브랜치 생성

1. `$ARGUMENTS`가 비어 있지 않으면 그 값을 브랜치 이름으로 사용한다.
2. 비어 있으면:
   - "어떤 기능을 개발할 건가요?"라고 묻는다.
   - 답변을 바탕으로 **영어 소문자-하이픈 형식**(예: `save-news`, `category-filter`)의 이름을 제안하고, 사용자가 확인하거나 수정하게 한 뒤 사용한다.
3. 브랜치 이름이 `^[a-z0-9]+(-[a-z0-9]+)*$` 형식인지 검사한다. 맞지 않으면 올바른 형식으로 고쳐서 제안한다.
4. 같은 이름의 브랜치가 이미 있으면(`git branch --list <이름>`) 알리고 다른 이름을 요청한다.
5. `git checkout -b <브랜치-이름>`으로 생성하고 이동한다.

## 3단계: 개발 시작 안내

1. 브랜치 생성이 끝나면 **"이제 개발을 시작하세요!"** 라고 안내한다.
2. `CLAUDE.md`를 읽고 이 프로젝트의 기술 스택과 컨벤션을 다시 한번 정리해서 알려준다. 최소한 다음을 포함한다:
   - 기술 스택: Next.js 16 / React 19 (App Router), Clerk(인증), Neon + Drizzle ORM(DB), Claude API(`claude-haiku-5-5`), Notion MCP, Tailwind 4, Vercel 배포
   - 컨벤션: `src/` 아래 `@/*` 별칭, 도메인 로직은 `src/lib/`, 변경은 Server Action(각 액션에서 `auth()` 재확인), DB/`auth()`를 읽는 페이지는 `<Suspense>` 안에서 처리(`cacheComponents`), 모든 행은 Clerk `userId`로 범위 지정
   - 작업 전 확인: Next.js 코드는 `node_modules/next/dist/docs/` 가이드를 먼저 읽기, UI는 `ui.md`, 기능 요구사항은 `PRD.md`
   - 명령어: `npm run dev`, `npm run build`(타입 체크 포함), `npm run lint`, `npm run db:generate`, `npm run db:migrate`
3. 안내 후 사용자가 개발을 진행하도록 기다린다. 사용자가 개발 요청을 하면 평소처럼 돕는다.

## 4단계: 완료 처리 (사용자가 `완료` 또는 `done` 입력 시)

1. `git status`와 `git diff --stat`으로 **변경된 파일 목록**(추가/수정/삭제, untracked 포함)을 보여준다.
2. 변경 내용을 바탕으로 **커밋 메시지를 자동으로 제안**한다. 최근 `git log --oneline` 스타일(한국어, 간결한 한 줄)을 따른다.
3. "이 메시지로 커밋하고 main에 병합할까요?"라고 묻고 **사용자의 확인을 기다린다.** 수정 요청이 있으면 반영한다.
4. 확인되면:
   - `.env*`, 자격 증명 등 비밀 정보가 담긴 파일은 커밋하지 않는다. 있으면 경고한다.
   - 변경 파일을 명시적으로 `git add` 하고 `git commit` 한다. 커밋 메시지 끝에는 세션 시스템 알림에서 지정한 Co-Authored-By 줄을 붙인다.
   - `git checkout main` 후 `git merge <브랜치-이름>`으로 병합한다.
   - 충돌이 나면 멈추고 충돌 파일을 알린 뒤 사용자와 해결 방법을 정한다. 임의로 강제 해결하지 않는다.
5. 푸시(`git push`)와 브랜치 삭제는 사용자가 요청하기 전에는 하지 않는다. 필요하면 다음 단계로 제안만 한다.

## 5단계: 작업 요약

병합이 끝나면 다음을 요약해서 보여준다:

- 브랜치 이름과 병합 결과(커밋 해시, 메시지)
- 변경된 파일 목록과 각 파일의 핵심 변경 내용
- 구현한 기능 설명 (1~3문장)
- 후속 작업 제안: `CLAUDE.md`의 진행 상황 갱신 필요 여부, 푸시, 작업 브랜치 삭제 여부
